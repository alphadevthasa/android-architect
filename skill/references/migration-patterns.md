# Migration patterns

How a migration is cut into safe steps. The playbooks in `catalog/playbooks/` and the plan generated by `scripts/migration-plan.js` follow these patterns. A plan is a skeleton: the order and the tags are deterministic, the explanation is written by the planner.

## Patterns

- **Seam.** Put a small interface between callers and the old implementation first, with no behavior change. Every later step swaps what is behind the seam. A migration without a seam cannot be reverted in pieces.
- **Strangler fig.** The new implementation grows around the old one and takes over unit by unit. The old code stays alive and reachable until the last unit moved, then it is deleted in a final, separate step.
- **Side by side.** Both implementations exist in the same build for a while. They must never both own the same state at the same time (see the single-writer rule below).
- **Feature flags.** A flag chooses the implementation per unit. Keep the flag value in saved state, so a process restart in the middle of a flow does not switch implementations. Remove the flag with the old code, not before.
- **Per-unit cutover.** A unit is a screen, a feature, a table or a call site, as the playbook defines it. One unit per pull request. A unit is done when its tests pass on the new implementation and the old path for that unit is unreachable.

## Rules the playbooks follow

- **Single writer.** At any moment exactly one implementation writes a given store or owns a given binding. Either all legacy code goes through the new library's connection, or the cutover of that store is all-at-once. Per-feature dual writing against one file loses data.
- **Backup before the first release.** Irreversible migrations (on-device data moves) take a full backup, including write-ahead and shared-memory files where the store has them, before the first release that opens the store with the new library.
- **No early deletion.** The old store, keys and code stay until the new path was verified and one full release cycle passed.
- **Safety nets first.** Characterization tests and screenshot tests for a feature exist before its first migration step. In the generated plan, every migration step of a pilot feature depends on its `safety-net:<feature>` step.
- **Human decisions stay visible.** Steps tagged `irreversible` or `decision` keep the tag through every expansion. Features with high risk get `decision` on all their steps: ask before touching them.

## How the plan generator expands steps

The generator reads a validated `recommendations.json`. It refuses to plan when the recommendations have violations.

- Steps of these dimensions are expanded once per feature, in bucket order (`first`, then `next`): `ui`, `presentation`, `navigation`. The expansion set is the constant `EXPAND_DIMENSIONS` in `scripts/lib/migplan.js`. Features in the `last` bucket get no step and a note `leave as is`.
- Steps of `persistence`, `keyvalue`, `networking` and `serialization` with a matching playbook form the data track: one global step each, carrying the playbook id, with `irreversible` and `decision` from the playbook.
- Other dimensions (for example `async` and `di`) are global enabling steps, carrying the playbook id when one matches.
- A step matches a playbook when dimension, `from` and `to` are equal. A transitive hop (a justification skips entries) matches nothing; plan each hop separately.
- An expanded step depends on the same feature's expansion of each prerequisite step when that prerequisite was expanded, otherwise on the prerequisite's single step id.
- `extract:design-system` appears when the duplication score is `medium` or `high`; UI feature steps depend on it.
- At most 40 features are planned per run; the rest are reported as "and N more".
