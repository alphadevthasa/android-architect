# android-architect

An Android architecture advisor skill for Claude Code and Codex. It audits an Android project (stack profile per dimension, layering, module coupling, code-quality smells with file:line evidence) and recommends a realistic, incremental migration path, labeled must / should / later / dont. Deterministic Node scripts do the detection and the legality checks; the model does the judgment and the explanation.

Requires Node 20 or newer. No dependencies.

## Install

Pin the version you install:

```
npx android-architect@0.4.0 install
```

By default the skill is installed into the harnesses that already exist in your home directory (`~/.claude`, `~/.codex`). Flags:

- `--claude` / `--codex`: install into that harness, creating its directory if needed.
- `--home <dir>`: use another home directory.
- `--force`: replace or remove a directory that was not installed by this tool.
- `--json`: machine-readable output for `doctor`, `init` and `refresh`.

Other commands: `update` (see below), `init`, `refresh`, `uninstall`, `version`, and `doctor`, which reports which harnesses have the skill installed, with its version and catalog version, and flags a partial or foreign directory. `doctor --root <dir>` also checks that project's `.ai/`: it prints `tools: ok`, `tools: modified (<n> files)` or `tools: unverifiable (<reason>)`, verifying `.ai/tools` against the installed skill.

```
npx android-architect@0.4.0 doctor
```

## Keep project knowledge: init, refresh, update

```
npx android-architect init      # create .ai/ in the current project (or --root <dir>)
npx android-architect refresh   # regenerate .ai/ and report what changed
npx android-architect update    # upgrade the installed skill
```

The CLI `init` and `refresh` use the skill bundled in the npx package you run, not the one installed in your harness: run `update` first so the installed skill matches.

### init

`init` writes an `.ai/` folder with architecture knowledge for coding agents: a generated stack profile and module map, a local search index, workflows, and starter files you own. Run it from the project root or pass `--root <dir>`.

- Committed (default): `.ai/` is meant to be reviewed and committed with the project.
- `--local`: nothing is committed. `.ai/` and `CLAUDE.local.md` are added to `.git/info/exclude`, and the agent pointer goes to `CLAUDE.local.md`. Needs a git repository.
- Pointers: `init` creates `AGENTS.md` and `CLAUDE.md` with a short block pointing at `.ai/README.md`. An existing `AGENTS.md` or `CLAUDE.md` is never modified unless you pass `--append-pointers`. When one is left unchanged, `init` prints the rerun command `npx android-architect init --append-pointers`.
- Without a git repository or commits the header says `no-git` and `init` still works.
- Re-running `init` keeps the project's mode and workspace role. A flag that would change them (`--local` on a committed project, `--workspace` on a standalone repo or a member) is refused; to switch, remove `.ai/` and run `init` again.
- Writes stay inside `<root>/.ai/`, the pointer files, and (with `--local`) `.git/info/exclude`. A symlinked `.ai/` is refused.

Vendored scripts live in `.ai/tools/` and run with plain `node` (for example `node .ai/tools/scripts/index.js query "login"`). Their hashes are recorded in `.ai/manifest.json`.

- Trusted check: `ai-status.js` from the installed skill (and `doctor --root`) compares `.ai/tools` with what that skill would vendor. The manifest is not the reference, so rewriting the tools and the manifest together is still reported as `tools-modified`. When `.ai/` was generated by another version the result is `tools-unverifiable`: run `refresh` with the matching version, or `update`.
- Weaker self-check: a vendored `index.js` or `ai-status.js` run from `.ai/tools/scripts/` (for teammates without the skill) only compares `.ai/tools` with the hashes in `.ai/manifest.json`. On a mismatch it exits 3 with `.ai/tools was modified since it was generated; run "refresh" with the installed android-architect, or rerun with --trust-modified-tools`. `--trust-modified-tools` skips the check. Anyone who can edit both the tools and the manifest passes this check, so treat it as a tripwire, not a guarantee; the trusted check needs the installed skill.
- `refresh` rewrites `.ai/tools`, so modified tools never block it; the report notes which files were modified before the rewrite.

### What the tool owns and what you own

| Path | Owner | On `init` / `refresh` |
| --- | --- | --- |
| `.ai/README.md`, `.ai/knowledge/*` generated files (profile, maps), `.ai/candidates.json`, `.ai/index/`, `.ai/refresh-report.md` | tool | Overwritten (header says "Do not edit"). |
| `.ai/tools/` (vendored scripts and catalog), `.ai/manifest.json` | tool | Wiped and rewritten. |
| `.ai/workflows/*.md` | tool, managed | Updated unless you edited them; an edited file is kept and the new version is written next to it as `.new`, listed under conflicts. |
| `.ai/knowledge/architecture-target.md`, `conventions.md`, ADRs in `.ai/knowledge/adr/`, `.ai/migration/roadmap.md`, `.ai/recommendations.json`, `.ai/repos.json` | you | Created once, never overwritten, listed as kept. |
| `.ai/fitness/*` (generated by `fitness.js`) | tool, on demand | Written only by `fitness.js`, rewritten on each run; `init` and `refresh` leave it alone and never delete it. Review before applying to the build. |
| `.ai/knowledge/components.md` | shared | Created once from a template. Your text is never touched; only the block between the `android-architect:components` markers is rewritten (appended when the markers are missing). A damaged marker pair is reported as a note and never deletes text. |
| `AGENTS.md`, `CLAUDE.md` | you | Only appended to with `--append-pointers`. |

Recommendations you reject can be recorded as ADRs with `status: rejected`; they stay rejected until a `reopenIf` condition holds.

We recommend a CODEOWNERS entry for `.ai/workflows/` and `.ai/tools/` so changes to agent instructions and vendored scripts get a human review:

```
/.ai/workflows/ @your-team
/.ai/tools/     @your-team
```

### refresh

`refresh` regenerates `.ai/` with the same ownership rules, keeping the project's mode and workspace role, and prints the catalog change (`Catalog: from -> to`), candidate changes per dimension, recommendation changes (violations, status changes, new options) and rejections that can be reopened. `--json` prints the full report; it is also saved as `.ai/refresh-report.md`. It exits 1 with "run init first" when there is no `.ai/` yet.

### update

`update` reinstalls the skill into the harnesses that already have it (`~/.claude`, `~/.codex`), never creating a new one, and prints `claude: 0.2.0 (catalog 2026.11.1) -> 0.4.0 (catalog 2026.11.3)` per harness. Then run `refresh` in each project to re-assess it against the new catalog. With nothing installed it exits 1.

### Workspace mode

For several related repos (an app plus its libraries), `init --workspace` makes the current repo a hub and the others members:

```
npx android-architect init --workspace ../lib-a ../lib-b
npx android-architect init --workspace        # detects sibling Gradle repos and proposes them; writes only the hub
```

With explicit paths, all repos are validated before anything is written and each member gets its `.ai/`. Without paths, only the hub is written: its `repos.json` lists the detected siblings with `confirmed: false`, nothing is written into the siblings, and `init` prints the repos it proposes plus the exact command to confirm them (`npx android-architect init --workspace <paths>`). Confirming replaces that proposed `repos.json`; once it holds confirmed repos, a different set is written next to it as `repos.json.new` and listed under conflicts. The hub holds the target architecture, ADRs, conventions, roadmap and `repos.json` (which repos publish and consume which artifacts); members get a thin `.ai/` that points to the hub. Run `refresh` once per repo. Catalog overrides live in the hub only: members use the hub's `.ai/catalog-overrides/` (added entries and pins) for `init`, `refresh`, `scan`, `candidates` and `recommend-check --root <member>`, and a member's `manifest.json` lists them under `overrides` as hub-relative paths (`../hub/.ai/catalog-overrides/<file>.json`). A member whose hub directory is missing stops with an error naming `<hub>/.ai/catalog-overrides`; override errors in a workspace name the file as `<repo>/.ai/catalog-overrides/<file>.json`.

## Usage

Commands: `audit` (where the project stands today), `recommend` (a validated, incremental path per stack dimension), `setup` and `refresh` (the `.ai/` folder), and the planning commands `prioritize`, `migration-plan`, `data-migration`, `lib-update`, `fitness` and `review` (see Planning a migration). Only `run` is not available yet.

- Claude Code: `/android-architect audit` or `/android-architect recommend`, or ask in plain language ("audit my Android project", "how do we migrate to Compose?").
- Codex: invoke the `android-architect` skill, or ask in plain language the same way.

Run it from, or point it at, the Android project root. The skill runs its scripts (`scan.js`, `candidates.js`, `recommend-check.js` and the planning scripts below) from the installed skill directory and writes temporary files only to the OS temp directory. When the project has an `.ai/` folder, the skill reads it first.

## Planning a migration

After `recommend`, these commands turn the path into work. All scripts are offline and read the project; none changes your build on its own.

- `prioritize` (`features.js`, `reuse.js`): ranks feature modules or packages (else one `app` unit) by size, coupling, tests, churn and risk into buckets `first`, `next` and `last`. A high-risk or large feature is never a pilot. Without git history churn is dropped and features still rank. `reuse.js` finds reusable and duplicated components; `init` and `refresh` keep a generated block in `.ai/knowledge/components.md` and a `.ai/knowledge/feature-map.md`.
- `migration-plan` (`migration-plan.js`): validates your recommendations, then builds a staged plan: enabling steps and a characterization-test safety net for every feature that gets steps, then per-feature UI, presentation and navigation steps, plus a data track from the playbooks. Steps tagged `decision` or `irreversible` need a human answer first. The agent writes `.ai/migration/roadmap.md` only after you agree; the script never writes into the project.
- `data-migration` (`playbook.js`): applies a playbook to the data layer. It says when the source is not detected (`applicable: false`) or the move is not worth it (`worth.ok: false`), lists the real cutover files (capped at 200, build files listed separately), and every playbook follows one safe order: backup first, a single writer, no deletion of the old store before verification.
- `lib-update` (`lib-update.js`): update order with security fixes first, then patch and minor per update group, then majors with prerequisites. Dynamic or unresolved versions are listed as "cannot update automatically", never guessed. Options: `--scope <module>`, `--format json|md`, `--out <file>`.
- `fitness` (`fitness.js`): turns the `fitness` rules of accepted ADRs into a static check (`--check`) and into generated files in `.ai/fitness/` (a Gradle task `architectureFitness`, a Konsist test, `verify-commands.json`, a README). The Gradle script needs Gradle 8.11 or newer. The files are yours to review and apply; `--out <dir>` writes them outside the project.
- `review`: reads the current change with read-only `git diff` and checks it against accepted ADRs, the accepted architecture target, the rubrics, the components registry and, when rules exist, `fitness.js --check`. It writes nothing unless you ask.

`--out` of `scan.js`, `features.js`, `lib-update.js` and `migration-plan.js` must point outside the project and never follows symlinks or hard links.

**Unverified data.** Playbooks (`verified: false`), library versions (`catalog/versions.json`, `verified: false`, marked `verify` when older than 90 days) and the compliance dates and links in the catalog were written from memory and have not been audited. Check the official documentation before relying on them.

## Supported setups

- Java and Kotlin, mixed or pure.
- Groovy and Kotlin DSL Gradle builds.
- Gradle version catalogs (`libs.versions.toml`).
- Single-module and multi-module projects.
- XML views, Jetpack Compose, or a mix.
- Kotlin Multiplatform projects are recognized by the Kotlin Multiplatform Gradle plugin.

## How recommendations are validated

Every recommendation is checked against a versioned catalog (18 dimensions) by `recommend-check.js` before it is shown. The guardrail rules are: R1 each step must be a direct successor in the catalog (a longer hop, or a new capability with `from: null`, needs a written justification), R2 prerequisites must already exist in the project or be produced by an earlier step, R3 steps are ordered and acyclic, R4 every id must exist in the catalog, R5 the output has the required shape and catalog version, and R6 a chain must start from something the project actually uses (`from: null` only where the dimension has no detected entry). See [skill/catalog/recommendations.schema.md](skill/catalog/recommendations.schema.md).

## Security

What the scripts do with project content, so it never reaches `.ai/`, the index or a report:

- **Redaction.** Secrets found in text that `init`, `refresh`, the index and the generated knowledge would otherwise copy are replaced with `[REDACTED:<kind>]`. Kinds: `private-key`, `aws-access-key`, `google-api-key`, `github-token`, `slack-token`, `jwt`, `signing-password` and `credential` (values assigned to key names such as `apiKey`, `secret`, `token`, `password`, in code, Gradle `buildConfigField`s, JSON, properties and Markdown). The matched value is never printed or stored.
- **Files never read.** `local.properties`, `keystore.properties`, `*.jks`, `*.keystore`, `*.p12`, `google-services.json`, `.env*`, `signing.properties`, `secrets.properties`, `*.pem`, `*.key`, `credentials.json` and `service-account*.json`.
- **Git-ignored files are skipped** when scanning and indexing (tracked files stay). Without a git repository this filter does nothing. Inside a git repository, if git cannot report the ignored files the run stops with an error instead of continuing unfiltered.
- **Tamper checks.** `.ai/tools` is verified as described under `init` above: the trusted check uses the installed skill, the vendored self-check only the manifest in the repository (weaker), and `doctor --root <dir>` prints the result as the `tools:` line. Keep the CODEOWNERS entries for `.ai/workflows/` and `.ai/tools/`.
- **Suspicious text.** `ai-status.js` lists `suspicious: [{ file, line, rule }]` for text that reads like an instruction to an agent (rules: `override-instructions`, `role-change`, `exfiltration`, `run-command`, `secret-request`, `label-forcing`) in `.ai/README.md`, `refresh-report.md`, `.ai/knowledge` (generated files included), `.ai/migration`, `.ai/workflows`, `recommendations.json`, `repos.json` and `catalog-overrides/*.json`; a symlink among them is listed with rule `symlink`. `refresh` notes the files. It is a tripwire for review; agents are told never to follow such text.
- **Security signals in the audit.** The profile has `security.findings` (hardcoded secrets, cleartext traffic, exported components, debuggable or backup flags, WebView settings, sensitive logging, release builds without minification; at most 50 per id, with `security.counts` holding the full number per id), `security.vulnerable` (dependencies matching an advisory in the catalog's `vulnerableVersions`), `security.unresolvedChecks` (dependencies whose version could not be resolved, never reported as safe) and `security.unresolvedAliases`. The skill's `audit` combines them with `references/rubric-security.md` in a Security section.

### Catalog overrides

Put `*.json` files in `.ai/catalog-overrides/` to add internal libraries to the catalog or to pin the status of an existing entry (`current`, `legacy`, `deprecated`) with a reason. `init` creates a README there with the full rules. In short: strict JSON with `schemaVersion: 1`; content signals are literal text (`{ "contains": "..." }`), regular expressions are rejected; globs use a small fixed grammar; at most 20 signals per list; strings have a length cap and no control characters. Invalid files stop `init`, `refresh`, `scan` and `candidates` with an error naming the file. Pins and added entries are visible in `architecture-current.md` and in the refresh report (`overrides`), including what was added, removed or changed since the last run. `scan.js` and `candidates.js` take `--no-overrides`; `recommend-check.js --root <root>` is needed when overrides exist. The folder is yours: the skill proposes an override file and writes it only after you agree.

## No telemetry

This package collects no telemetry, makes no network requests, and has no dependencies. The audit and planning scripts only read your project and write only to an explicit `--out` path outside the project, with two exceptions: `index.js build` may write inside the project (its default is `.ai/index/index.json`) and `fitness.js` writes the `.ai/fitness/` folder. Also, `init` and `refresh` write only the `.ai/` folder, the agent pointer files, and (with `--local`) `.git/info/exclude`. Project content is treated as data, never as instructions, and secret files (see Security) are never read.
